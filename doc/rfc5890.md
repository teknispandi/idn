# RFC 5890
**RFC 5890 — Internationalized Domain Names for Applications (IDNA): Definitions and Document Framework** 

# Tujuan & Ruang Lingkup

RFC 5890 mendefinisikan **istilah kunci dan kerangka dokumen** untuk keluarga IDNA2008 (RFC 5890–5895, 5892, 5893). Ia tidak menjelaskan algoritme validasi secara lengkap—itu ada di RFC lain—namun 5890 menyepakati **apa yang dimaksud “label”, “A-label”, “U-label”, “LDH”, “dot”,** dan “slot” tempat nama domain dipakai atau disimpan.

# Istilah Paling Penting

* **DNS Label**: segmen di antara “titik” dalam nama domain (mis. `www`, `例え`, `xn--caf-dma`).
* **LDH label**: label klasik berisi huruf Latin a–z, digit 0–9, dan hyphen `-` (Letter-Digit-Hyphen).
* **NR-LDH label** (*Non-Reserved LDH*): LDH label yang:

  * tidak diawali/diakhiri `-`,
  * **tidak** memiliki `--` pada posisi ke-3 dan ke-4 (untuk menghindari bentrok prefix ACE `xn--`),
  * panjang 1–63 byte.
* **A-label**: representasi **ASCII** dari label IDN menggunakan ACE/Punycode dengan **prefix `xn--`**. Inilah yang **disimpan dan dikirim** lewat DNS (karena DNS hanya ASCII).

  * Contoh: `café` → `xn--caf-dma`
* **U-label**: representasi **Unicode** manusiawi dari label yang **ketika diubah** (ToASCII/IDNA) menghasilkan A-label yang setara.

  * Contoh: `例え` (U-label) ↔ `xn--r8jz45g` (A-label)
* **Dot Equivalence** (pemisah label): selain `.` (U+002E), ada tiga “titik” yang **dipersempit setara** di UI:

  * U+3002 (IDEOGRAPHIC FULL STOP)、U+FF0E (FULLWIDTH FULL STOP)、U+FF61 (HALFWIDTH IDEOGRAPHIC FULL STOP).
  * Aplikasi boleh memperlakukan semuanya sebagai pemisah label yang sama.
* **Case**: IDNA bekerja dalam **lowercase**; canonicalisasi huruf dilakukan sebelum konversi.

# “Slot” Penggunaan Nama Domain

5890 membedakan **konteks (slot)** agar tidak rancu:

1. **DNS slot** – hanya **A-label** (ASCII/ACE) yang valid.
2. **Stored slot** – basis data/konfigurasi; *boleh* simpan A-label atau U-label sesuai kebijakan, tapi harus konsisten.
3. **User-interface slot** – input/output ke pengguna; biasanya **U-label** untuk keterbacaan, dengan kebijakan keamanan (mis. fallback A-label bila berisiko phishing).

# Hubungan Dengan RFC Lain (IDNA2008)

* **RFC 5891**: Protokol/algoritme (ToASCII/ToUnicode), kapan konversi dilakukan, aturan panjang, dll.
* **RFC 5892**: Tabel **kategori code point** (PVALID, CONTEXTJ, CONTEXTO, DISALLOWED, UNASSIGNED).
* **RFC 5893**: Aturan **Bidi** untuk skrip kanan-ke-kiri (Arab/Ibrani) agar tata letak aman.
* **RFC 5894**: Rationale & panduan desain.
* **RFC 5895**: *Mapping* (mis. normalisasi ringan) yang **opsional** untuk aplikasi.

> Intinya: 5890 = **definisi & kerangka istilah**; 5891/5892/5893 menentukan **boleh/tidaknya** karakter dan proses konversi.

# Aturan Umum Panjang & Struktur

* Setiap **label** (setelah dikonversi ke A-label) maksimal **63 oktet**.
* Nama domain penuh maksimal **255 oktet** dalam wire format DNS (termasuk panjang & terminator).
* A-label selalu **`xn--` + punycode**; U-label harus **mencerminkan** A-label yang ekuivalen.

# Siklus Konversi (Aplikasi)

1. **Input UI (U-label/teks)** → normalisasi & pemeriksaan → **ToASCII/IDNA** → **A-label**.
2. **Resolusi DNS** memakai **A-label**.
3. **Output UI**: **ToUnicode** dari A-label ke U-label jika aman/diizinkan kebijakan.

Contoh:

* Pengguna mengetik `bücher.example` → app menghasilkan `xn--bcher-kva.example` untuk query DNS → hasil ditampilkan lagi sebagai `bücher.example` di UI.

# Perbedaan IDNA2003 vs IDNA2008 (yang ditegaskan 5890)

* **Karakter “diizinkan”** berubah dari pendekatan tabel statis ke **kategori berbasis properti Unicode** (via 5892) + **aturan kontekstual**.
* **Mapping agresif** (upper → lower, width folding, dll.) yang dulu *implicit* menjadi **opsional/eksplisit** (5895).
* **Aturan Bidi** diperketat (5893).
* Penanganan **UNASSIGNED** berubah (umumnya **tidak diizinkan** sampai rilis Unicode berikut disahkan lewat pembaruan tabel 5892).

# Kebijakan Registry vs Aplikasi (yang ditekankan 5890)

* **DNS** tidak tahu “skrip” atau “bahasa”; itu urusan kebijakan registry/aplikasi.
* Registry boleh menetapkan aturan tambahan (varian, bundling, skrip tunggal, larangan campur skrip, dll.) **di atas** IDNA (mis. melalui LGR).
* Aplikasi **tidak boleh** mengasumsikan semua U-label dapat dipakai; harus lewat **ToASCII** dan patuh 5891/5892/5893.

# Keamanan & Usability (ringkas)

* **Homograf**: karakter berbeda tampak mirip; 5890 mengingatkan UI untuk kebijakan tampilan (mis. tampilkan A-label jika campur skrip mencurigakan).
* **Dot equivalence** memudahkan UX tetapi implementasi harus tegas saat **konversi**.
* **Case folding & NFC**: lakukan sebelum ToASCII agar deterministik.

# Contoh Praktis

* **café.id**

  * U-label: `café`
  * A-label: `xn--caf-dma`
* **例え.テスト**

  * `例え` → `xn--r8jz45g`
  * `テスト` → `xn--zckzah`
* **Nama dengan “titik CJK”**: `例え。テスト` (U+3002) di UI diperlakukan sama seperti `例え.テスト`.

# Implikasi Untuk Anda (registry/ops)

* **Simpan canonical**: pilih simpan A-label di database sebagai “sumber kebenaran”; sediakan tampilan U-label di UI.
* **Validasi**: lakukan **ToASCII** (5891) + **cek kategori 5892** + **Bidi 5893** sebelum provisioning. (Aturan tambahan—LGR/varian—diterapkan setelah lulus IDNA).
* **UI**: normalisasi ke **lowercase**, konversi “dot” ekivalen, dan kebijakan tampilan aman (mis. fallback ke A-label bila ada campur skrip/indikasi risiko).
* **Interop**: semua yang “on-the-wire” ke DNS harus **A-label**.

# FAQ Singkat

**Q: Apakah DNS bisa menyimpan Unicode langsung?**
A: Tidak. DNS menyimpan **ASCII**; IDN dikirim sebagai **A-label** (ACE/punycode).

**Q: Kapan saya pakai U-label?**
A: Di **UI** dan mungkin **penyimpanan aplikasi**; selalu verifikasi via ToASCII → A-label.

**Q: Bagaimana dengan panjang label Unicode?**
A: Yang dihitung untuk batas 63 adalah **A-label** (setelah dikonversi).

**Q: Bolehkah campur skrip?**
A: IDNA tidak otomatis melarang, tetapi **5892/5893** bisa membatasi; registry **boleh** menetapkan larangan/aturan tambahan.
