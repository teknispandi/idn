# RFC 5891
**RFC 5891: “Internationalized Domain Names in Applications (IDNA): Protocol”**, yaitu dokumen inti dari seri **IDNA2008**.
Kalau **RFC 5890** mendefinisikan istilah dan konsep, **RFC 5891** adalah **aturan operasional dan algoritma konversi IDN**, khususnya proses **ToASCII** dan **ToUnicode** yang digunakan untuk validasi dan transformasi label Unicode menjadi bentuk DNS yang valid (A-label).

Berikut penjelasan **lengkap dan rinci** dari RFC 5891:

---

## 🧭 1. Tujuan Utama RFC 5891

RFC 5891 menjelaskan **bagaimana aplikasi dan registry harus memproses, memvalidasi, dan mengonversi** nama domain berisi karakter Unicode agar bisa digunakan di DNS.

Karena DNS hanya mendukung **ASCII**, maka semua nama beraksara non-Latin (seperti aksara Jawa, Arab, Han, Cyrillic, dll.) harus **diubah menjadi ASCII Compatible Encoding (ACE)** melalui **Punycode**, dengan awalan `xn--`.

Proses dan aturan di RFC 5891 memastikan bahwa:

* Domain IDN yang berbeda di permukaan (U-label) tidak menghasilkan representasi DNS berbeda secara semantik.
* Tidak ada karakter “aneh” atau berbahaya (security risk, spoofing, dll.).
* Konsistensi antara UI, database, dan DNS terjaga.

## ⚙️ 3. Proses Utama: ToASCII dan ToUnicode

Dua fungsi utama dalam RFC 5891:

### 🔹 ToASCII

Digunakan untuk mengubah **U-label** (Unicode label) → **A-label** (ACE/Punycode)
Langkah-langkahnya:

1. **Input**: Sebuah label (bukan nama domain lengkap) dalam bentuk Unicode.
2. **Cek karakter “dot”** (`U+002E`, `U+3002`, `U+FF0E`, `U+FF61`) dan **pisahkan label per dot**.
3. **Validasi kategori karakter** menggunakan tabel dari RFC 5892:

   * PVALID (Allowed)
   * CONTEXTJ/CONTEXTO (kontekstual, perlu aturan tambahan)
   * DISALLOWED
   * UNASSIGNED
4. **Cek panjang label Unicode** (harus ≥1 dan ≤63 karakter setelah konversi).
5. Jika label **hanya LDH**, tidak perlu dikonversi (contoh: `example` tetap `example`).
6. Jika mengandung non-ASCII:

   * Konversi ke NFC (Normalization Form C).
   * Uji karakter Bidi (jika RTL).
   * Encode ke Punycode + tambahkan prefix `xn--`.
7. Hasil akhir disebut **A-label**, yang bisa dikirim ke DNS.

### 🔹 ToUnicode

Dipakai untuk mengubah **A-label** (ASCII) → **U-label** (Unicode).
Langkah-langkahnya:

1. Jika label tidak diawali `xn--`, kembalikan apa adanya.
2. Jika diawali `xn--`, lakukan **decode punycode**.
3. Hasil decode diverifikasi:

   * Apakah karakter hasil decode sesuai RFC 5892/5893.
   * Jika tidak valid, tampilkan label `xn--...` (bukan hasil decode).
4. Return hasil Unicode (U-label) untuk tampilan di UI.

> ⚠️ RFC 5891 menekankan: ToUnicode **tidak pernah gagal dengan error**, tapi **“failsafe”**: kalau hasilnya invalid, tetap tampilkan input awal (A-label).

---

## 📦 4. Proses Validasi Domain Lengkap (Full Domain Name)

Untuk nama domain seperti `bücher.example.com`:

1. Pisahkan menjadi label: `bücher`, `example`, `com`.
2. Untuk setiap label:

   * Jalankan **ToASCII**.
   * Pastikan hasil A-label panjang ≤ 63 byte.
3. Gabungkan dengan “.” → `xn--bcher-kva.example.com`.
4. Cek total panjang domain (≤ 255 byte).
5. Domain siap dikirim ke DNS.

---

## 🧱 5. Prinsip “Labels are independent”

Setiap label domain diproses **secara independen**; RFC 5891 melarang interpretasi lintas-label.

Contoh:

* `例え.テスト`

  * `例え` → `xn--r8jz45g`
  * `テスト` → `xn--zckzah`
* Keduanya diproses secara terpisah sebelum digabung.

---

## 🧮 6. Aturan Panjang

* Label Unicode (sebelum encode): ≥ 1 code point.
* Label hasil encode (A-label): ≤ 63 byte.
* Nama domain penuh (gabungan semua label + titik): ≤ 255 byte.

---

## 🧰 7. Error dan Kondisi Invalid

RFC 5891 menetapkan beberapa jenis **error** yang harus ditangani aplikasi:

| Kategori Error               | Penyebab                                                                  |
| ---------------------------- | ------------------------------------------------------------------------- |
| **Disallowed**               | Ada karakter yang bukan PVALID/CONTEXT                                    |
| **Context Error**            | Karakter CONTEXTJ/CONTEXTO muncul tapi aturan kontekstual tidak terpenuhi |
| **Bidi Error**               | Label melanggar aturan arah teks (5893)                                   |
| **Too Long**                 | A-label > 63 byte                                                         |
| **Empty Label**              | Label kosong (misalnya “..”)                                              |
| **Unassigned**               | Karakter belum ditetapkan di Unicode                                      |
| **Mapping Error (optional)** | Jika implementasi 5895 digunakan dan mapping gagal                        |

---

## 🧩 8. Konteks Karakter (Contextual Rules)

Dijelaskan di RFC 5892, tetapi RFC 5891 menegaskan **kapan** harus diterapkan:

### ContextJ (Joiner)

* Misal: ZERO WIDTH JOINER (U+200D)
  Hanya valid di posisi tertentu (misalnya di antara huruf skrip Indic).

### ContextO (Other)

* Misal: MIDDLE DOT (U+00B7) hanya valid di antara huruf “l” Latin kecil (misal `al·l` dalam bahasa Catalan).

Aplikasi harus **mengevaluasi aturan kontekstual** setiap kali karakter dengan kategori CONTEXT muncul.

---

## 🔤 9. Bidi Rules (Ringkas)

Berlaku bila label mengandung karakter RTL (Arab, Ibrani):

1. Label boleh berawalan karakter RTL.
2. Semua karakter lain harus RTL atau numerik (dengan pembatas aturan).
3. Label tidak boleh bercampur arah berbahaya.
4. Label LTR (Latin, Han, dll.) tidak boleh mencampur RTL di posisi sembarangan.

RFC 5893 mengatur detailnya, tapi RFC 5891 menyebutkan bahwa implementasi **wajib** menolak label yang melanggar aturan Bidi.

---

## 🧾 10. Registry & Policy Hooks

RFC 5891 tidak mendefinisikan kebijakan pendaftaran, tetapi:

* **Registry dapat menambahkan layer tambahan** (mis. LGR, varian, kebijakan skrip tunggal, bundling, dsb.).
* RFC 5891 hanya memastikan label sudah “IDNA-valid”.
* Setelah lulus IDNA-validasi, baru boleh dicek ke kebijakan registry.

Contoh: `.id` bisa saja menolak label campur skrip Latin + Jawa meskipun IDNA memperbolehkan.

---

## 🔐 11. Keamanan

RFC 5891 menyoroti risiko:

* **Homograf** (karakter mirip visual tapi berbeda Unicode, mis. `а` Cyrillic vs `a` Latin).
  → UI harus waspada dan mungkin menampilkan A-label.
* **Phishing** dengan kombinasi skrip (Latin + Cyrillic).
* **Panjang atau bentuk abnormal** (mis. titik ganda).

---

## 💡 12. Contoh Implementasi

### Input:

```
bücher.de
```

### Langkah:

1. Pisahkan: [`bücher`, `de`]
2. `bücher` mengandung non-ASCII → ToASCII:

   * Normalize (NFC)
   * Validasi PVALID
   * Encode → `xn--bcher-kva`
3. `de` → tetap `de`
4. Gabung → `xn--bcher-kva.de`

## 🧩 13. Perbedaan dengan IDNA2003

RFC 5891 (IDNA2008) memperbaiki masalah dari IDNA2003:

| Aspek           | IDNA2003                                | IDNA2008                                       |
| --------------- | --------------------------------------- | ---------------------------------------------- |
| Mapping         | Otomatis (case, width, fullwidth, dll.) | Tidak otomatis (diserahkan ke 5895, opsional)  |
| Daftar karakter | Berdasarkan tabel statis                | Berdasarkan properti Unicode                   |
| Bidi            | Tidak diatur jelas                      | Ditetapkan di RFC 5893                         |
| Error handling  | Longgar                                 | Lebih ketat dan deterministik                  |
| UNASSIGNED      | Boleh                                   | Dilarang sampai Unicode berikut validasi ulang |

---

## 🧭 14. Lifecycle di Aplikasi (End-to-End)

```plaintext
User Input (UI)
  ↓
Normalize (NFC, mapping opsional 5895)
  ↓
Split per dot (5890)
  ↓
For each label:
   - Validate via 5892 (PVALID/CONTEXT)
   - Apply 5893 (Bidi)
   - ToASCII (5891)
  ↓
Join labels → domain
  ↓
Query DNS (pakai A-label)
  ↓
Display (ToUnicode → U-label jika aman)
```
