# RFC 5892
**RFC 5892**, yaitu bagian paling teknis dan *“engine utama”* dari keluarga **IDNA2008**.
RFC ini berjudul:

> **RFC 5892 — The Unicode Code Points and Internationalized Domain Names for Applications (IDNA)**

dan berfungsi sebagai **“Character Table & Rulebook”** untuk menentukan *karakter mana* di Unicode yang **boleh** (PVALID), **tidak boleh** (DISALLOWED), atau **bersyarat** (CONTEXTJ / CONTEXTO) digunakan dalam **Internationalized Domain Names (IDN)**.

---

# 🧭 1. Tujuan RFC 5892

RFC 5892 menjelaskan **kriteria teknis** untuk memutuskan apakah suatu **code point Unicode** dapat dipakai dalam nama domain (U-label), sesuai standar **IDNA2008**.

Kalau RFC 5890 adalah “kamus istilah”, dan RFC 5891 adalah “protokol proses”, maka **RFC 5892 adalah “aturan siapa yang boleh masuk klub IDN”**.

Singkatnya:

> RFC 5892 = algoritma penentuan status code point (boleh / tidak) berdasarkan properti Unicode resmi.

---

# 🧩 2. Latar Belakang

DNS bekerja dengan **huruf Latin ASCII**.
IDNA memungkinkan aksara lain (Arab, Han, Jawa, Devanagari, dst.) melalui Unicode.
Namun tidak semua karakter Unicode aman untuk digunakan — banyak yang mirip, tidak terlihat, atau punya fungsi tertentu (mis. control char, format, atau diakritik berbahaya).

Maka dibutuhkan **filter ketat berbasis properti Unicode**, bukan daftar statis.

---

# ⚙️ 3. Struktur Kategori Utama RFC 5892

Setiap code point Unicode diklasifikasikan ke dalam salah satu kategori berikut:

| Kategori                               | Arti                                                                 |
| -------------------------------------- | -------------------------------------------------------------------- |
| **PVALID (Protocol Valid)**            | Aman dan diizinkan digunakan dalam label IDN                         |
| **CONTEXTJ (Contextual Rule: Joiner)** | Hanya boleh jika konteks tertentu terpenuhi (mis. ZERO WIDTH JOINER) |
| **CONTEXTO (Contextual Rule: Other)**  | Sama seperti CONTEXTJ, tapi untuk karakter lain (mis. MIDDLE DOT)    |
| **DISALLOWED**                         | Tidak boleh digunakan                                                |
| **UNASSIGNED**                         | Belum didefinisikan dalam versi Unicode yang digunakan               |

---

# 🧠 4. Prinsip Dasar Penentuan Kategori

RFC 5892 **tidak memuat daftar karakter satu per satu**, tetapi memberikan **aturan berbasis properti Unicode**.
Implementasi (misalnya library `idna2008`) akan membaca data Unicode (misalnya `UnicodeData.txt`, `DerivedCoreProperties.txt`, `Scripts.txt`) dan menghitung kategori tiap karakter dengan algoritma ini.

### 4.1. Langkah umum:

1. Ambil **code point** `X`.
2. Cek versi Unicode resmi (mis. Unicode 5.2 untuk RFC asli).
3. Ambil properti dari `X`:

   * General Category (`Ll`, `Lo`, `Nd`, dll.)
   * Script (`Latin`, `Arabic`, `Han`, dll.)
   * Derived properties (Join_Control, Combining Mark, dll.)
4. Terapkan aturan berikut (berurutan).

---

# 🧾 5. Aturan Klasifikasi (Inti RFC 5892 §2)

Berikut ringkasan aturan yang menentukan kategori akhir:

## 🟩 Rule A: PVALID (Protocol Valid)

Code point menjadi **PVALID** jika memenuhi salah satu:

### A.1 Huruf dan angka “normal”

* General Category:
  `Ll`, `Lu`, `Lo`, `Lm`, `Mn`, `Nd`, `Mc`
* Tidak memiliki properti `Default_Ignorable_Code_Point`
* Tidak berstatus `Join_Control`
* Tidak didefinisikan sebagai `combining mark` yang berbahaya (mis. isolasi tanda)

### A.2 Karakter kategori `Other_Letter` (Lo)

* Biasanya huruf utama dari suatu skrip (Latin, Devanagari, Han, Jawa, Bali, dll.)

### A.3 Angka (Nd)

* Semua angka native tiap skrip (mis. `०१२३`, `๐๑๒๓`, `١٢٣٤`).
* Tapi **tidak boleh mencampur** angka dari skrip berbeda dalam satu label.

---

## 🟨 Rule B: CONTEXTJ

Beberapa karakter hanya valid **dalam konteks tertentu**, terutama pengendali penyambung (joiner).

Dua karakter paling penting:

1. **U+200C ZERO WIDTH NON-JOINER (ZWNJ)**
2. **U+200D ZERO WIDTH JOINER (ZWJ)**

Valid *hanya jika* digunakan dengan konteks yang sesuai, misalnya:

* di antara huruf dalam skrip Indic, Arab, atau Persia,
* bukan di awal/akhir label,
* bukan di tempat tanpa karakter yang dapat bergabung.

Jika konteks tidak terpenuhi → **DISALLOWED**.

---

## 🟨 Rule C: CONTEXTO

Karakter lain yang valid **hanya** dalam konteks tertentu. Contohnya:

| Code Point                   | Nama                              | Konteks                                                    |
| ---------------------------- | --------------------------------- | ---------------------------------------------------------- |
| U+00B7                       | MIDDLE DOT                        | Hanya valid di antara “l” (Latin kecil) → mis. `al·là`     |
| U+0375                       | GREEK LOWER NUMERAL SIGN (KERAIA) | Hanya valid di depan huruf Yunani                          |
| U+05F3, U+05F4               | Ibrani Geresh/Gershayim           | Hanya valid di posisi akhir                                |
| U+30FB                       | Katakana Middle Dot               | Hanya valid di label yang seluruhnya Katakana/Hiragana/Han |
| U+0660–U+0669, U+06F0–U+06F9 | Angka Arab                        | Tidak boleh dicampur antara bentuk Timur dan Barat         |

Jika kondisi tidak terpenuhi, label dianggap **tidak valid**.

---

## 🟥 Rule D: DISALLOWED

Code point menjadi **DISALLOWED** jika:

* Termasuk **control characters** (`Cc`, `Cf`, `Cs`, `Co`).
* Termasuk **space separators** (`Zs`).
* Termasuk **symbols dan punctuations** (`Ps`, `Pe`, `Sm`, `Sc`, `Sk`, `So`, `Pc`, dll.).
* Termasuk **Hangul Jamo individual** (karena digunakan hanya dalam kombinasi).
* Termasuk **compatibility characters** (fullwidth forms, etc.).
* Termasuk **surrogate code points** (`U+D800–U+DFFF`).
* Termasuk **private-use** (`U+E000–U+F8FF` atau Plane 15–16).
* Termasuk **Combining mark berbahaya** (mis. tanda non-spacing di awal label).

---

## ⚪ Rule E: UNASSIGNED

Jika code point **belum didefinisikan** di versi Unicode yang digunakan oleh implementasi IDNA → statusnya **UNASSIGNED**.
Label berisi UNASSIGNED **harus ditolak**.

# 📜 7. Aturan Tambahan (Appendix A)

RFC 5892 menyediakan **daftar lengkap aturan** yang bisa diterapkan otomatis oleh generator tabel IDNA.
Setiap rule diberi kode seperti:

* **A.1**: Derived property “LetterDigitsHyphen” → PVALID
* **B.1**: ContextJ = ZWJ/ZWNJ
* **C.1.2**: ContextO = MIDDLE DOT
* dan seterusnya.

Implementasi praktis seperti `idna-data` (Python) atau `go-idna` menggunakan data ini untuk membangun **tabel lookup**.

---

# 🧩 8. Integrasi dengan RFC 5891

RFC 5891 (protokol) **memanggil RFC 5892** saat melakukan validasi.

Prosesnya:

```
Input U-label
 → Normalize (NFC)
 → Loop tiap code point:
       category = getCategoryFrom5892(codepoint)
       if DISALLOWED or UNASSIGNED → reject
       if CONTEXTJ/CONTEXTO → check contextual rule
 → If semua valid → lanjut ToASCII (Punycode)
```

---

# 🔐 9. Alasan Desain

RFC 5892 menggunakan **property-based algorithm**, bukan daftar tetap, agar:

1. Bisa mendukung Unicode baru tanpa menulis ulang seluruh tabel.
2. Fleksibel untuk semua skrip di dunia.
3. Aman terhadap karakter baru yang berpotensi menimbulkan *spoofing*.
4. Mendorong implementasi otomatis berbasis data Unicode.

---

# ⚠️ 10. Implikasi untuk Registry (mis. PANDI)

Untuk sistem registry atau validator IDN `.id`:

✅ Gunakan hasil RFC 5892 untuk memastikan **karakter valid secara protokol IDNA2008**
❌ Jangan mendaftarkan label yang mengandung:

* Karakter `DISALLOWED`
* Karakter `UNASSIGNED`
* Karakter CONTEXTJ/CONTEXTO tanpa verifikasi konteks

Contoh penerapan di sistem registry `.id`:

* Sebelum menerapkan **LGR Aksara Jawa**, pastikan semua karakter dalam daftar LGR adalah **PVALID atau CONTEXTO valid** menurut RFC 5892.
* Jika ada karakter **DISALLOWED**, maka LGR harus memberi justifikasi atau tidak memasukannya sama sekali.

---

# 🧭 11. Contoh Implementasi (Pseudo-code)

Berikut logika dasar implementasi RFC 5892:

```go
func ValidateCodePoint(r rune) string {
    if isUnassigned(r) {
        return "UNASSIGNED"
    }
    if isJoinControl(r) {
        return "CONTEXTJ"
    }
    if isContextualOther(r) {
        return "CONTEXTO"
    }
    if isLetterOrDigit(r) && !isDisallowedByOtherRules(r) {
        return "PVALID"
    }
    return "DISALLOWED"
}
```

# 🔍 12. Perbedaan IDNA2003 vs IDNA2008 (RFC 5892)

| Aspek             | IDNA2003                                | IDNA2008 (RFC 5892)                  |
| ----------------- | --------------------------------------- | ------------------------------------ |
| Basis             | Daftar statis karakter dari Unicode 3.2 | Algoritma properti Unicode dinamis   |
| Pembaruan Unicode | Harus revisi RFC baru                   | Otomatis (hanya update data Unicode) |
| Contextual rules  | Tidak ada                               | Ada (ContextJ / ContextO)            |
| Bidi & diakritik  | Tidak jelas                             | Dikontrol ketat oleh RFC 5893        |
| Mapping           | Agresif (case folding otomatis)         | Tidak otomatis, opsional RFC 5895    |

---

# 🧾 13. Inti Singkat RFC 5892

| Aspek            | Penjelasan                                                   |
| ---------------- | ------------------------------------------------------------ |
| Tujuan           | Menentukan karakter Unicode mana yang boleh di IDN           |
| Keluaran         | Kategori: PVALID, CONTEXTJ, CONTEXTO, DISALLOWED, UNASSIGNED |
| Basis            | Properti Unicode (General Category, Script, Derived)         |
| Diterapkan oleh  | RFC 5891 (ToASCII / ToUnicode)                               |
| Fokus keamanan   | Hindari karakter tak terlihat, campur skrip, simbol berisiko |
| Dapat diperbarui | Ya, mengikuti versi Unicode baru                             |
| Dampak           | Dasar bagi semua LGR dan kebijakan registry IDN              |

---

# 📘 14. Hubungan RFC 5892 dengan LGR (Label Generation Rules)

Ketika membuat **LGR untuk aksara daerah** (mis. Jawa, Bali, Batak), langkah pertama adalah:

1. Ambil seluruh karakter aksara dari Unicode.
2. Jalankan filter RFC 5892:

   * Ambil hanya PVALID atau CONTEXTO valid.
3. Terapkan aturan tambahan (WLE, varian, dll.) untuk kebutuhan registry.

Jadi RFC 5892 = **lapisan dasar universal** sebelum aturan lokal (LGR) diberlakukan.

# 🧩 15. Contoh Praktis dari Unicode Script

### Contoh 1 — Aksara Latin

Semua huruf kecil dan besar Latin dasar (a–z, A–Z, dengan diakritik) → **PVALID**

### Contoh 2 — Aksara Jawa

* `ꦏ` (U+A98F) → Lo → **PVALID**
* `ꦴ` (U+A9B4) → Mc (combining mark, vokal) → **PVALID**
* `꧀` (U+A9C0) → Mn (virama) → **PVALID**
* `U+200C` (ZWNJ) → **CONTEXTJ** (valid bila di antara karakter Indic)
* `U+0020` (spasi) → **DISALLOWED**
