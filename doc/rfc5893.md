# RFC 5893
**RFC 5893 – “Right-to-Left Scripts for Internationalized Domain Names for Applications (IDNA)”**, yaitu bagian **keempat** dari rangkaian standar **IDNA 2008 (RFC 5890–5895)**.

Kalau tiga RFC sebelumnya (5890, 5891, 5892) mengatur struktur, protokol, dan kategori karakter, **RFC 5893** berfokus pada **aturan Bidi (bidirectional text rules)** — yaitu **bagaimana menangani label domain yang mengandung aksara kanan-ke-kiri (Right-to-Left / RTL)** seperti Arab, Ibrani, Urdu, Persia, dsb.

---

## 🧭 1. Tujuan RFC 5893

Tujuan utamanya adalah **mencegah tampilan salah atau menipu** (spoofing) akibat perilaku teks dua arah (bidirectional) di Unicode.

Masalahnya:

> Unicode bisa mencampur karakter **LTR (Left-to-Right)** seperti Latin dengan **RTL** seperti Arab.
> Tanpa aturan tambahan, domain seperti `abc.مثال` atau `123.שלום` bisa ditampilkan terbalik di UI browser atau email client.

RFC 5893 menetapkan **aturan ketat (Bidi Rule)** agar **label IDN** dengan karakter RTL **tetap stabil, aman, dan konsisten tampilannya**.

---

## 🧩 2. Latar belakang teknis: Unicode Bidi

Dalam Unicode, setiap karakter memiliki properti arah:

| Properti | Arah                 | Contoh skrip      |
| -------- | -------------------- | ----------------- |
| **L**    | Left-to-Right        | Latin, Devanagari |
| **R**    | Right-to-Left        | Ibrani            |
| **AL**   | Right-to-Left Arabic | Arab, Urdu        |
| **EN**   | European Number      | 0–9               |
| **AN**   | Arabic Number        | ٠١٢٣٤             |
| **NSM**  | Non-Spacing Mark     | Tanda diakritik   |

Aplikasi seperti browser atau terminal memakai algoritme **Unicode Bidirectional Algorithm (UBA)** untuk menampilkan teks dengan campuran arah ini.
Masalah muncul karena urutan tampilan bisa **berbeda dari urutan logis** — misalnya `.abc.שלום` dapat terlihat terbalik jika aturan tidak jelas.

---

## ⚙️ 3. Prinsip dasar Bidi Rule (IDNA)

RFC 5893 menetapkan bahwa **setiap label** (bagian di antara titik) harus:

1. **Memiliki arah dominan yang konsisten**, dan
2. **Tidak menyebabkan tampilan label ambigu**.

Semua pemeriksaan Bidi dilakukan **setelah normalisasi (NFC)** dan **sebelum ToASCII (Punycode)**, seperti pada alur RFC 5891.

---

## 🧾 4. Dua kelas utama label

| Tipe Label    | Didefinisikan oleh karakter pertama valid                                       | Aturan berlaku                      |
| ------------- | ------------------------------------------------------------------------------- | ----------------------------------- |
| **L-label**   | Label yang **dimulai dengan karakter L** (Latin, Han, Katakana, Hiragana, dll.) | Tidak boleh ada karakter RTL (R/AL) |
| **RTL-label** | Label yang **dimulai dengan karakter R atau AL** (Ibrani, Arab, dll.)           | Aturan RTL yang ketat (lihat bawah) |

---

## 🔹 5. Aturan untuk **L-Label**

(Label yang dominan kiri-ke-kanan)

1. **Karakter pertama** harus bertipe **L**.
2. Semua karakter dalam label harus bertipe salah satu dari:

   * **L** (Left-to-Right)
   * **EN** (European Number)
   * **ES**, **CS**, **ET** (simbol numerik seperti `-`, `+`, `.`, `,`)
   * **ON** (Other Neutral)
   * **NSM** (Non-Spacing Mark)
3. **Tidak boleh ada** karakter bertipe **R** atau **AL** (Right-to-Left / Arabic Letter).

📌 Artinya: Label Latin atau Indonesia seperti `café-id` aman, tapi label `abcع` (campur Arab) **invalid**.

---

## 🔸 6. Aturan untuk **RTL-Label**

(Label yang dominan kanan-ke-kiri)

Ini bagian inti RFC 5893 §2.
Label dianggap RTL jika karakter pertama memiliki arah **R** atau **AL**.

### Aturan RTL-Label:

1. **Karakter pertama** harus R atau AL.
2. **Karakter terakhir** harus:

   * R, AL, EN, atau AN
     (tidak boleh diakhiri tanda baca atau neutral murni).
3. Semua karakter di tengah label boleh salah satu dari:

   * R, AL, AN, EN, ES, CS, ET, ON, NSM
4. **Tidak boleh mencampur EN (European Number) dan AN (Arabic Number)** dalam label yang sama.
   (Mis. label dengan `1` Latin dan `١` Arab bersama-sama → ditolak.)
5. **NSM (non-spacing mark)** hanya boleh muncul **setelah** karakter R, AL, EN, AN, atau NSM lain.
6. **Tidak boleh ada karakter L (Left-to-Right)** sama sekali.

## 📘 7. Ringkasan aturan dalam bentuk tabel

| Label type    | First char | Last char  | Disallowed content | Mixed digits    | L allowed? |
| ------------- | ---------- | ---------- | ------------------ | --------------- | ---------- |
| **L-label**   | L          | bebas      | R/AL               | boleh campur EN | ✅          |
| **RTL-label** | R/AL       | R/AL/EN/AN | L                  | ❌ tidak boleh   | ❌          |

## 🧮 8. Algoritma Bidi Check (ringkas)

RFC 5893 §2.6 menyediakan algoritma pemeriksaan label (disederhanakan):

```
function CheckBidi(label):
  first = getFirstBidiClass(label)
  if first == L:
     if any(R or AL in label): invalid
  else if first in [R, AL]:
     if not last in [R, AL, EN, AN]: invalid
     if contains(L): invalid
     if containsBoth(EN, AN): invalid
  else:
     invalid (label must start with L or R/AL)
```

## 🧩 9. Contoh valid dan tidak valid

| Label                                        | Deskripsi              | Valid?                      | Alasan                         |
| -------------------------------------------- | ---------------------- | --------------------------- | ------------------------------ |
| `שלום`                                       | Semua Ibrani (R)       | ✅                           | RTL konsisten                  |
| `abc`                                        | Latin (L)              | ✅                           | L-label                        |
| `שלום1`                                      | Arab/RTL + angka Eropa | ✅                           | R + EN boleh (tidak campur AN) |
| `שלום١`                                      | Arab/RTL + angka Arab  | ✅                           | R + AN boleh                   |
| `שלום1١`                                     | Campur EN dan AN       | ❌                           | Mixed digits                   |
| `abcع`                                       | Latin + Arab           | ❌                           | L-label dengan karakter R/AL   |
| `عabc`                                       | Arab + Latin           | ❌                           | RTL-label dengan karakter L    |
| `־שלום` (Ibrani dengan punctuation di depan) | ❌                      | Tidak boleh diawali neutral |                                |

## 🧠 10. Alasan di balik aturan ini

* Unicode memungkinkan teks RTL dan LTR bercampur;
  tanpa aturan, urutan visual bisa menipu.
* Misalnya domain `paypal.com` dapat ditulis dengan karakter RTL di tengah untuk menyembunyikan `.com`.
* RFC 5893 mencegah hal ini dengan **melarang pencampuran arah dalam satu label**.

Jadi aturan ini **bukan untuk linguistik**, tapi **keamanan dan determinisme tampilan**.

---

## 🧱 11. Hubungan dengan RFC 5891 dan 5892

Ketika aplikasi memproses label Unicode:

1. **Normalize NFC** →
2. **Cek kategori (5892)** →
3. **Jika mengandung karakter R/AL**, jalankan **Bidi Rule (5893)** →
4. Jika lolos, lanjutkan **ToASCII** (5891) untuk encode ke punycode.

Implementasi validator IDN modern (mis. `idna` Python, `x/net/idna` Go) mengikuti urutan ini.

---

## 🧩 12. Konteks numerik (EN vs AN)

Karakter angka Eropa (`0–9`) bertipe **EN**, sedangkan angka Arab-Indic (`٠١٢٣٤`) bertipe **AN**.
RFC 5893 melarang campurannya untuk mencegah tampilan bercampur orientasi atau kesalahan pengucapan.

Misalnya:

```
U+0661 (١) dan U+0031 (1)
```

terlihat mirip, tapi arah dan asal skrip berbeda → harus dipisahkan per label.

---

## 🔐 13. Keamanan dan tampilan

Beberapa vektor serangan yang dihindari:

* **Label reversal spoofing** — teks RTL membuat label tampil terbalik.
* **Visual deception** — karakter campuran menyebabkan titik “terpindah”.
* **Confusion mixing digits** — “paypal.com” vs “moc.lapyap”.

RFC 5893 memastikan semua label tampil dalam urutan visual yang sama di semua sistem.

---

## 📦 14. Implementasi di Registry (mis. PANDI)

Untuk registry `.id` yang mungkin nanti mendukung **skrip Arab Jawi**, **Urdu**, atau **Ibrani**:

✅ Terapkan **validasi Bidi** untuk setiap label RTL.
❌ Tolak label campuran LTR–RTL dalam satu label.
✅ Boleh gabung domain RTL dan LTR di tingkat berbeda (`مثال.id` valid, tapi `id.مثال` tergantung kebijakan).

Ingat: aturan berlaku **per label**, bukan per domain utuh.

## 📋 15. Ringkasan Inti RFC 5893

| Aspek                | Penjelasan                                                      |
| -------------------- | --------------------------------------------------------------- |
| Tujuan               | Mencegah ambiguitas tampilan label RTL                          |
| Diterapkan pada      | Label dengan karakter bertipe R atau AL                         |
| Label tipe           | L-label dan RTL-label                                           |
| Mixed scripts        | Dilarang campur LTR dan RTL dalam satu label                    |
| Mixed digits         | Dilarang campur EN dan AN                                       |
| Validasi waktu       | Setelah 5892 (kategori) dan sebelum ToASCII                     |
| Fokus utama          | Keamanan tampilan & interoperabilitas UI                        |
| Pengaruh ke registry | Validasi wajib untuk skrip RTL (Arab, Ibrani, Urdu, Jawi, dll.) |

## 🧮 16. Contoh hasil validasi lengkap (alur)

```
Input:  "سلام123"
Normalize (NFC)
 → contains Arabic (AL) → RTL label
CheckBidi:
   - first char AL ✅
   - last char EN ✅
   - contains only AL, EN ✅
   - no L characters ✅
Result: Bidi valid
ToASCII → "xn--123-f7la" (contoh punycode)
```

---

## 📖 17. Hubungan dengan RFC 5895 (mapping)

RFC 5893 dilakukan **sebelum** mapping opsional di 5895.
Mapping hanya menyentuh bentuk input (case folding, width).
Aturan Bidi tetap wajib diterapkan sesudah semua normalisasi selesai.

---

## 🧭 18. Kesimpulan

**RFC 5893** memastikan bahwa:

* Label IDN dengan skrip kanan-ke-kiri **tidak membingungkan visual**,
* **Tidak mencampur arah atau jenis angka**,
* dan tetap **aman & konsisten di semua platform**.

Tanpa aturan ini, domain RTL berpotensi memunculkan **phishing, spoofing, dan visual reversal attacks**.
